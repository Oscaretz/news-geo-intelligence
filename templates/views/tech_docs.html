1. Topología de la Arquitectura

La solución se apoya en un ecosistema de microservicios Dockerizados que orquestan el ciclo de vida del dato analítico.

imageDiagrama / Captura
Flask (Web): Proporciona endpoints RESTful asíncronos y sirve la interfaz frontend construida con Tailwind CSS y Vanilla JS.
PostgreSQL (OLAP Storage): Motor persistente central, configurado con esquemas transaccionales para raw data y tablas relacionales orientadas a análisis.
Dagster Webserver (UI): Expone el panel de control gráfico de Dagster, permitiendo trazar linaje de datos y monitorear el estado de los runs en tiempo real.
Dagster Daemon: Coordinador de ejecución en background que maneja la persistencia de colas, retries y schedulers.

2. Pipeline ETL y Orquestación (Dagster)

La lógica de negocio asíncrona está encapsulada en Software-Defined Assets (SDAs) de Dagster (etl/definitions.py). Este orquestador coordina las recolecciones de información y los motores de inferencia masiva.

imageDiagrama / Captura

El flujo inicia extrayendo metadatos no procesados, los cuales se agrupan y paralelizan hacia los nodos computacionales (LLM). Si ocurre una falla irrecuperable en un lote, el sistema descarta los registros en una Dead Letter Queue (DLQ) local para inspección manual, permitiendo que el pipeline principal continúe sin afectar la integridad del DAG.

3. Modelo de Datos

El almacén implementa un esquema en estrella (OLAP Star Schema) diseñado para maximizar el rendimiento (throughput) de las lecturas analíticas en el frontend.

imageDiagrama / Captura
fact_news_metrics: Tabla de hechos conteniendo la granularidad atómica por artículo (conteo de palabras, sentimiento).
Tablas de Dimensión: dim_date, dim_source, dim_entities.

La ingesta utiliza lógica idempotente mediante operaciones UPSERT (ON CONFLICT DO UPDATE o DO NOTHING), garantizando que las reejecuciones del ETL no generen duplicados ni violaciones de primary keys.

4. Integración de Modelos (LLMs)

La inferencia semántica se fundamenta en un flujo híbrido tolerante a fallos a través de las SDKs de Groq y Gemini (Flash).

imageDiagrama / Captura

El sistema emplea Prompt Engineering estricto para forzar la salida de JSON validable. Los esquemas Pydantic dictan el contrato de datos esperado. Instrucciones específicas fuerzan al modelo a limpiar variaciones lingüísticas y jerga (como "Edomex") hacia vectores estandarizados ("Estado de México"), garantizando uniones (joins) relacionales precisas en la fase de mapeo geográfico.

5. Asistente Conversacional (RAG)

El motor integra un asistente analítico avanzado que permite consultar el modelo relacional subyacente.

imageDiagrama / Captura
Streaming API: Implementado vía Server-Sent Events (SSE) nativos en Flask para el renderizado asíncrono y progresivo de las respuestas en el frontend, evitando timeouts HTTP.
Inyección de Contexto: El LLM recibe dinámicamente un volcado serializado de métricas y acceso a las ejecuciones históricas para responder utilizando la técnica Retrieval-Augmented Generation.

6. Capa de Catálogos (GeoJSON & i18n)

El sistema expone configuraciones modulares permitiendo escalar la plataforma horizontalmente sin modificar el código base.

imageDiagrama / Captura
Caché en Memoria (Geometrías): Las topologías territoriales se precargan (geojson_cache.py) desde map_config.json y archivos vectoriales estáticos, reduciendo dramáticamente el consumo de I/O en la renderización de Leaflet.
Internacionalización (i18n): El frontend abstrae un diccionario inyectado que permite conmutar claves data-i18n mediante iteradores JavaScript en el cliente.

7. Despliegue y Repositorio

El despliegue está contenerizado. Los comandos operativos principales son los siguientes:

# 1. Clonar el repositorio
git clone <repository_url>
cd google_news_scraping

# 2. Configurar variables de entorno
cp .env.template .env
# Editar .env (DATABASE_URL y API Keys: GROQ, GEMINI)

# 3. Construir y levantar servicios
docker-compose up -d --build
